# sutecoでのBehavProof利用・効果測定

対象元ソースは [`kanoi-y/suteco@79bbcaab`](https://github.com/kanoi-y/suteco/tree/79bbcaab65539a1f5d080a98710e52bf06764283)。**現行コードで再現できる独立した問題を3件確認した。** 元の製品コード・既存テストは変更せず、測定用コピーに条件と観測処理を追加した。問題のある入力・以前の保存状態は検証用に構成したもので、利用者の端末で過去に3件の事故が発生したという集計ではない。

## 基準値と追加検証

| 対象 | 結果 |
| --- | --- |
| 元のJestテスト | 32ファイル・181件成功、失敗0 |
| 元のTypeScript型検査 | 成功 |
| 追加した条件 | 8条件：成功5・失敗3・未確認0 |
| 独立した原因として数える問題 | 3件 |
| 既知の正しい挙動を確認する対照 | 5条件すべて期待どおり |

5つの対照は、正常な取込み、不正な品目参照の拒否、内容も変わる版更新、HTTPSリンク、後続イベントでの自治体選択である。「対照で誤検出がなかった」はこの5条件についての結果であり、リポジトリ全体の誤検出率を推定したものではない。

## 再現した3件

| ID | 条件と実際の結果 | 影響・確かめた範囲 |
| --- | --- | --- |
| S1 | A自治体のデータにB自治体のルールを混ぜると、検証を通過してBの既存の区分・説明が上書きされる | 実際のSQLite保存結果と、アプリのRepositoryが返す結果まで確認。スキーマの不足と上書きを一原因として数えた |
| S2 | 配布データの版だけが変わると、起動後もDB・選択状態・保存状態・設定画面の版が古いままになる | 現行の配布版 `2025-09-01` に対し、保存済みの `2000-01-01` が残る。分別内容が古いという結果ではなく、版情報の更新漏れ |
| S3 | 参考リンクに `file:///tmp/suteco-study-only` を指定すると、画面からそのままネイティブのリンク起動処理へ渡される | 起動関数を記録用に差し替えて引数を確認。実際のファイル表示・外部アプリ起動・攻撃の成功は試していない |

S1の期待は「一つの自治体ファイルで他の自治体のルールを変更しない」という所有範囲の条件である。仕様書にID一致の式がそのまま書かれているわけではなく、自治体別ファイルと選択自治体に応じたルール表示の要件から明文化した。原因は[スキーマの整合性検査](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/src/schema/municipality-dataset-schema.ts#L28-L72)に自治体IDの対応がなく、[取込み処理](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/src/lib/dataset/import.ts#L51-L77)が各ルールのIDをそのまま使うこと。正常データは取り込め、不明な品目の参照は状態を変えず拒否される対照も確認した。

S2では[起動時の判定](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/src/components/InitializationProvider.tsx#L34-L40)が内容ダイジェストだけを比較し、[ダイジェストの対象](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/src/lib/dataset/content-digest.ts#L45-L52)に版が含まれない。内容も変えた対照では、同じ起動処理を通ってDB・保存状態・画面の版が新しくなった。過去に版だけの更新が配布されたことまでは調べていない。

S3は設計書の[「安全な外部リンクのみ開く」](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/docs/trash_sort_app_detailed_design.md#L733)に対応する。網羅的な許可スキームの定義はないため、ローカルファイルURIを外部ブラウザ用の参考リンクから除く条件にした。[画面の処理](https://github.com/kanoi-y/suteco/blob/79bbcaab65539a1f5d080a98710e52bf06764283/app/items/%5Bid%5D.tsx#L61-L69)にはこの確認がない。HTTPSの対照は同じ経路で正しく渡る。データ供給経路への攻撃者のアクセスやOS側での処理は今回の主張に含まない。

## 数えなかった観測

`loadMunicipality(A)`の直後、同じイベント内でBを選ぶ、または選択を消すと、後からAの読込み結果で戻されることもAPI単体では再現した。しかし現行のSQLite読込みは同期的で、実際の画面からその順序を起こせることは確認できなかった。後続のイベントでBを選ぶ対照ではBが維持された。この観測は3件に加算していない。

## BehavProofで確かめたこと

8条件を条件ID・期待値・対象版へ結び付け、`assurance run`が新しいJestプロセスを条件ごとに起動した。元の関数・Repository・SQLite・React画面を動かして得た生の値を返し、BehavProofが期待値との不一致を判定した。Jestの終了コードだけを条件の成否に読み替えていない。

Collectorが結果と生の観測を捕捉し、測定側ホストで成果物bytes・現在の入力ハッシュ・固定した検証基準を確認してから、公開の条件評価APIと保証マップAPIへ渡した。[保証マップ](results/assurance-map.md)には成功した条件と失敗した条件が残る。確認できないものを成功へ変更する設定緩和は行っていない。

2026-11-17の初回測定時点では、Jestは標準CLIゲートの対応対象に入っていなかった。初回の[プロジェクト検出結果](results/summary.json)は未対応であり、Jestの報告をVitestの報告と偽装してゲートを通してはいない。今回は公開APIを使うローカル測定として実施した。初回測定だけでsutecoへの標準ゲート導入を完了した結果ではない。

2026-11-18に標準Jest連携を追加し、同じ元コミットへ適用した。元の181テストは32ファイルすべて成功し、認証済みの標準ゲートも成功した。追加条件は5成功・3失敗となり、ゲートは失敗を保持して拒否した。前記の到達未確認のAPI観測は実行対象から除外し、Jest上は1件のpendingとして残る（合計9登録、8実行）。ケースごとの接続処理は使わず、一つのJest実行で標準SDKのrunner/reporterとネイティブJSONをCollectorへ渡した。[標準連携の証拠](../../evidence/jest-suteco.json)と[再実行手順](../../jest.ja.md)を参照。

標準連携の今回1回のCollector実行時間は既存181件17.054秒、追加条件10.170秒。異なる接続方法・実行範囲を含むため、初回測定との速度倍率は示さない。製品ソース・既存テストへの変更は引き続き0。標準連携もローカルで独立して選択したホストの確認であり、suteco本番のCI保護を設定した結果ではない。

## 効果の読み方と導入コスト

既存181テストが成功する状態で追加した条件から、3つの見落としを再現できた。一方、**同じ再現テストをJestだけで実行しても問題は検出できる**。この実験から、BehavProofの不具合発見能力がJestや人によるテスト設計より優れているとは結論しない。要求の明文化・コード読解・追加テストの効果と、BehavProofによる条件・版・証拠・範囲の管理の効果を分けて読む必要がある。

| 実行・資材 | 測定値 |
| --- | --- |
| 既存181テスト | Jest報告14.761秒、1回の基準測定 |
| 同じ追加8条件をJestだけでまとめて実行 | 5成功・3失敗、全体3.339秒（Jest自身の報告2.158秒） |
| BehavProofの追加観測・収集 | 13.371秒・13.293秒・13.251秒、中央値13.293秒 |
| 元の製品ソース・既存テストへの変更 | 0ファイル |

3回とも条件別の判定は同じだった。時間はこのMac・固定版・ウォームな依存環境での局所的な値であり、一般的なCI時間の予測値ではない。既存テストはJest内部の報告時間、追加比較とBehavProofは起動から完了までの壁時計時間なので、基準測定との単純な倍率比較はしない。

手書き導入資材のファイル数・行数・ハッシュは[測定の補足](results/context.json)に記録した。再現テストだけで447行を要しており、単に設定を一つ加えた実験ではない。生成した[契約](generated/contracts.json)と[設定](generated/behavproof.config.json)も保存している。今回のJest接続は条件ごとに別プロセスを起動する構成であり、速度を最適化した標準アダプターではない。探索や契約作成にかかった人の時間、運用でのレビュー削減時間、全不具合に対する発見率は測っていない。

実機・カメラ・外部Gemini・本番の保存環境は対象外。Expoの既存テスト用アダプターを使い、SQLiteでは実SQLを実行する。AsyncStorageはメモリのテスト用実装、リンク起動は記録用実装である。新しい外部承認・CI上の発見・本番の完全保証を示す結果ではない。

## 再実行

Node20.19.4・pnpm10.29.3で、測定対象の固定版の依存をインストールしたコピーを用意する。BehavProof側はNode24でビルドする。

```sh
npm run build
node docs/studies/suteco-2026-11-17/measure.mjs /測定用/suteco /Node20.19.4/bin/node 3
```

この処理は測定用コピーへ観測ファイルを追加し、ローカルの `codex/behavproof-study` ブランチに記録する。sutecoへpushしない。生成した設定・契約・観測ファイルを含む測定コミットと、元の製品コミットを別々に記録する。[方法書](method.ja.md)、[独立レビュー](review.md)、[集計](results/summary.json)、[生の観測と成果物一覧](results/artifact-index.json)を合わせて参照できる。

修正する場合の最小案は、S1の自治体ID整合性検査、S2の版の同期条件、S3の表示・起動前のURI検査である。今回suteco本体の修正・公開は行っていない。
