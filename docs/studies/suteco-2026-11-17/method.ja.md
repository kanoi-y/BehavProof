# sutecoでのBehavProof導入効果の測定方法

対象は `kanoi-y/suteco` の `79bbcaab65539a1f5d080a98710e52bf06764283`。既存テストを変更せず、Node20.19.4・pnpm10.29.3と固定lockで実行する。BehavProofは当初 `6063bcd` で準備し、最終測定には導入候補1〜7と追加キャッシュ対策を含む `d15d08d961712877bd318245fb5d068581d890f4` を使った。

既存テストの成功数・失敗数を基準値とし、仕様書・設計書と実コードから条件を明文化して追加検証する。重点対象は自治体データの整合性・書込み範囲、データ版の更新、外部リンク。対照は正常データ取込み、不正な品目参照の拒否、内容も変わる版更新、HTTPSリンク、後続イベントでの自治体選択とする。品目検索は今回の追加条件に含めない。

「既存バグ」は、元の製品ソースを変更せずに、要求に反する観測を再現できた独立した原因だけを数える。一原因の複数ケースは一件。未再現の懸念、環境構築の失敗、人工的に挿入した故障、単なる不足証拠をバグ数へ足さない。コード読解で見つけた候補と、BehavProofによる条件評価の検出を区別し、ツール単独の自動発見率は主張しない。

新しい条件は人が定める必要がある。測定には実際のソース呼出しとSQLiteでの状態比較を使い、端末・カメラ・外部Geminiの実運用検証とは区別する。外部APIへ実画像や秘密情報を送らない。元のsutecoリポジトリへ修正や設定を公開せず、再現用コピーと導入用ファイル・結果を保存する。

Jestは標準CLIゲートの対応対象に入っていないため、既存Jestを維持し、`assurance run`と公開のCollector・条件評価・保証マップAPIを使う。Jest結果をVitest結果と偽装しない。観測処理を加えたローカル専用コミットで入力を固定し、製品ソースが元の版と一致すること、成果物bytes・現在の入力・明示した期待値を、測定側ホストで確認する。これはローカル測定の証拠であり、sutecoの本番ゲート導入完了や新しい人間の承認を意味しない。

集計項目は、既存テスト結果、追加した条件数、条件別のpass/fail/unknown、独立原因別の実バグ数、正常対照の誤検出、実行時間、導入ファイル数・行数、対象外範囲。全バグ数の分母は不明なため「全体の何％を発見」とは表現しない。
